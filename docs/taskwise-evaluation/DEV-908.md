# DEV-908 — Distributed Storage, Healing, and Recovery

**Project:** MinIO vs Silo — S3 Storage Evaluation (DEV-904)  
**Evaluation profile:** Option B — 8 CPU cores, 16 GiB RAM, at least 100 GiB SSD, 5–10 GiB test dataset; three workload repetitions per engine.

## 1. Executive Summary

This report examines distributed topology, service continuity, object availability, and recovery behavior, with MinIO-specific healing workflows as the principal study.

## 2. Evaluation Environment

The comparison design uses a single Ubuntu SSD-backed host, sequential execution of MinIO and Silo, equivalent S3 client configurations, consistent dataset manifests, and the same benchmark-tool release. Image digests, application configuration, workload parameters, and hardware inventory belong in the run record.

| Parameter | Common evaluation design |
|---|---|
| CPU | 8 cores |
| RAM | 16 GiB |
| Storage | At least 100 GiB SSD |
| Dataset | 5–10 GiB; small, medium, and large objects |
| Repetitions | 3 per engine |
| Execution order | MinIO, then Silo |
| Comparison rule | Identical input and test conditions |

## 3. Test Configuration

Use the four-node MinIO Compose topology. Define restart/failure scenarios, a stable test dataset, polling intervals, and time-to-recovery criteria. Compare only equivalent resilience behaviors when Silo topology supports them.

## 4. MinIO Results

MinIO distributed mode distributes data across configured drives and nodes; healing and availability depend on erasure layout and failure conditions.

## 5. Silo Results

Silo resilience should be described using its actual topology and supported recovery mechanisms rather than assuming MinIO-style erasure healing.

## 6. Feature/Performance Comparison

| Scenario | MinIO evaluation | Silo evaluation |
|---|---|---|
| Node restart | Availability and recovery interval | Equivalent supported fault case |
| Object readability | Sample object GET during disruption | Same object set |
| Repair | Healing progress and post-repair integrity | Product-specific recovery |
| Recovery | Time from restoration to healthy service | Same timing definition |

## 7. Technical Findings

A resilience result needs both availability observations and post-recovery integrity; recovery time alone omits data correctness.

## 8. Issues and Limitations

Four containers on one physical host do not represent independent physical fault domains.
